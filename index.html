Case studies

Where the risk was, and what I did about it.

Case 01 · Client project

Smart Parking Management

Web + mobile · Manual · Selenium (TestNG) · Postman · SQL

Money and time slots are where users lose trust fastest. That's where I spent the most effort.

Context
A booking system where drivers reserve a slot, pay and can cancel for a refund, on web and mobile.
Risk
Double charges, two drivers holding one slot and refunds that never arrive. Each one means an angry customer and a support ticket.
Approach
I owned QA for the whole reservation, booking, payment and cancellation flow. I designed negative cases for double booking, overlapping time slots, sessions expiring mid-payment, failed payments and refunds, then verified the data with Postman and SQL.
Result
Critical booking and payment defects were found and fixed before release. I then automated the regression suite so those flows stay covered on every release.

Case 02 · Client project

Estate Management System

Web + iOS + Android · Playwright · JavaScript · Manual

One product on three platforms has to behave like one product.

Context
A property platform with a web app and native iOS and Android apps, used by several roles with different permissions.
Risk
A user sees data they shouldn't, or the web and mobile apps disagree about the same record. Slow, flaky test runs that the team stops trusting.
Approach
I tested role-based access for each user type and checked that data, features and UI matched between web and mobile across devices and OS versions. I built Playwright tests that run in parallel on Chromium, Firefox and WebKit, using auto-waits and trace viewer.
Result
Fewer flaky test failures and faster cross-browser runs. When a test fails, the trace shows the cause.

Case 03 · Client projects

Point of Sale Systems

Web + mobile responsive · Playwright · Manual

I tested it the way a receptionist uses it on a Saturday afternoon, not the way the spec describes it.

Context
POS systems for appointment-based businesses: scheduling, checkout, discounts and receipts, on web and mobile.
Risk
Failures during peak hours: conflicting bookings, payments split across methods and a dropped connection at the till.
Approach
I built test scenarios around how staff actually work under pressure, covering time-slot conflicts, split payments, cancelled appointments and offline or slow networks. Then I automated the key flows with Playwright.
Result
Core checkout and scheduling flows are protected by automation and stay stable from one release to the next.
